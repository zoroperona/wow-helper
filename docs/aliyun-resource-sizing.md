# WoW Helper 阿里云资源规格建议

> 本文随云方案一并搁置，只保留历史容量建议。当前操作规范见 [常用运维手册](operations-runbook.md)，历史记录见 [操作日志](operations-log.md)。

## 1. 业务数据库是否上传 Git

不上传。

`loot-allocator.sqlite` 虽然目前来自本地应用，但它包含成员、装备快照、收益结果和分配记录。云服务正式启用后，ECS 上的文件将成为唯一生产主库。本地文件只用于首次迁移、开发或灾难恢复，不能再和云端双向写入或合并。

即使使用私有 GitHub 仓库，也不应提交业务数据库，原因包括：

- SQLite 是二进制文件，Git 无法有效审查差异或合并冲突。
- 每次小修改都可能产生一个新的完整对象，仓库历史会持续膨胀。
- 数据可能包含成员信息、管理员会话、审计日志和外部来源原始数据。
- Git 不是数据库备份系统，无法保证正在写入时得到一致性快照。
- 从 Git 历史彻底移除误提交的敏感数据很麻烦。

Git 中只维护数据库结构和迁移代码：

```text
migrations/
  001_initial.sql
  002_auth_sessions.sql
  003_audit_logs.sql
  004_character_sources.sql
```

生产数据的正确流向是：

```text
首次上线：本地一致性备份 -> ECS 校验并导入
正式运行：ECS 业务主库 -> OSS 定时加密备份
灾难恢复：OSS 指定备份 -> ECS 停服校验并恢复
```

切换到云端当天应设置明确的写入分界点：

1. 停止本地服务和本地写入。
2. 使用 SQLite Backup API 生成最终本地备份。
3. 校验 `PRAGMA quick_check` 和 SHA-256。
4. 导入 ECS，执行 migration 并验证数据数量。
5. 开放云端服务。
6. 此后本地页面只能访问云端 API，不能继续维护另一份可写 SQLite。

如果开发时需要样本数据，应从生产备份生成经过脱敏的开发数据库，不要直接使用生产主库，也不要把脱敏前文件提交 Git。

## 2. 当前容量与负载基线

截至 2026-08-19，本地数据量约为：

| 项目 | 当前大小 | 特征 |
|---|---:|---|
| 业务 SQLite | 15 MB | 低频读写，持续增长 |
| wow-db SQLite | 770 MB | 大量读取，按游戏 Build 整体替换 |
| wow-db 压缩交接包 | 约 140 MB | 每个游戏 Build 一份不可变资产 |
| SimC 运行产物 | 144 MB / 2 天 | 增长最快，需要清理策略 |
| 本地业务库备份 | 约 17 MB/份 | 可压缩并按周期保留 |

当前 SimC 配置每次使用 1000 iterations、默认 6 个线程，单任务最长允许 30 分钟。数据库本身不需要很高的 CPU 或内存，ECS 规格主要由 SimulationCraft 决定。

如果按当前两天 144 MB 的速度长期保留 SimC 文件，一年可能增长约 25–30 GB。因此必须设置本地保留周期，而不是单纯扩大云盘。

## 3. ECS 规格

### 3.1 推荐生产配置

适合当前团队规模，并允许单个 SimC 任务正常占用多核：

| 项目 | 推荐配置 |
|---|---|
| 实例 | 通用型或计算型 ECS |
| CPU | 4 vCPU |
| 内存 | 8 GiB |
| 操作系统 | Ubuntu 24.04 LTS x86_64 |
| 系统盘 | 40 GiB ESSD Entry 或同等级云盘 |
| 数据盘 | 80 GiB ESSD Entry/PL0，同地域独立数据盘 |
| 公网带宽 | 固定 3–5 Mbps，或按流量计费 |
| 实例数量 | 1 台 |

推荐 4 核的原因是 SimulationCraft 是主要计算负载。现有默认 6 线程在 4 核上可以运行，但建议上线时将默认线程调整为 4，避免模拟期间 Nginx 和 Node 接口明显卡顿。

8 GiB 内存用于同时容纳：

- Node 服务和缓存。
- Nginx。
- Playwright/Chromium 英雄榜会话。
- SimulationCraft。
- SQLite 页缓存和系统文件缓存。

80 GiB 数据盘可容纳业务库、当前和上一版 wow-db、SimC 短期产物、临时解压空间及本地备份。更新 770 MB 数据库时需要同时保留旧库、新库和压缩包，因此不能只按当前文件总大小配置。

### 3.2 经济型起步配置

如果希望先控制成本，可以使用：

| 项目 | 经济型配置 |
|---|---|
| CPU | 2 vCPU |
| 内存 | 4 GiB |
| 系统盘 | 40 GiB |
| 数据盘 | 40–60 GiB |
| 公网带宽 | 3 Mbps 或按流量计费 |

使用该配置必须同时调整：

- SimC 线程从 6 降到 2。
- 全局只运行一个模拟任务。
- 游客模拟严格限流和去重。
- Playwright 与 SimC 不同时执行高负载任务。
- 设置内存和 CPU 监控告警。

2 核 4 GB 能运行，但全量模拟会更慢，模拟期间页面响应也更容易受到影响。若游客可发起模拟，推荐直接使用 4 核 8 GB。

### 3.3 暂不推荐的配置

- 1 vCPU / 2 GiB：运行 Chromium 和 SimC 时余量不足。
- 突发性能型实例：长时间 SimC 可能耗尽 CPU 积分，性能不可预测。
- 仅使用系统盘：部署和数据生命周期耦合，重建 ECS 时更容易误删生产数据。
- 多台 ECS：SQLite 业务库不适合多实例并发写入，当前没有必要。

## 4. 云盘规划

建议使用独立数据盘，并挂载到：

```text
/srv/wow-helper/data/       # 业务主库和运行状态
/srv/wow-helper/wow-db/     # 当前及上一版 wow.sqlite
/srv/wow-helper/backups/    # 最近的本地业务备份
/srv/wow-helper/simc-runs/  # SimC 短期产物
/srv/wow-helper/sessions/   # 加密后的英雄榜会话
```

建议保留策略：

| 数据 | ECS 本地保留 |
|---|---|
| 业务数据库 | 始终保留当前主库 |
| 业务备份 | 最近 7 份 |
| wow-db | 当前版和上一版 |
| SimC JSON/Profile/日志 | 30 天 |
| SimC HTML 报告 | 7–14 天，或仅保留最新一份/角色 |
| 图标缓存 | 可清理并重新生成 |

SimC HTML 是当前增长较快的文件类型，单份约 1.5 MB。若网页只需要解析后的报告数据，不应永久保存全部 HTML。

云盘应开启阿里云自动快照，但云盘快照不能替代应用级 SQLite 备份。建议每天一次快照、保留 7 天；业务库仍需单独备份到 OSS。

## 5. OSS 规格与目录

### 5.1 Bucket 建议

| 项目 | 建议 |
|---|---|
| 存储类型 | 标准存储 |
| 地域 | 与 ECS 完全相同 |
| 访问权限 | 私有 |
| 版本控制 | 开启 |
| 服务端加密 | 开启，初期可使用 OSS 托管密钥 |
| 公共访问阻止 | 开启 |
| 传输 | 仅 HTTPS |

同地域 ECS 通过内网 Endpoint 访问 OSS，可以提高稳定性并减少公网流量。应用不应持有 Bucket 全权限，只授予指定前缀的上传、下载和列举权限。

建议目录：

```text
backups/business/YYYY/MM/DD/*.sqlite.gz
backups/business/manifests/*.json
releases/wow-db/<build>/<sha256>/*.zip
releases/wow-db/<build>/<sha256>/transfer-manifest.json
release-manifests/application/*.json
```

### 5.2 初期容量估算

当前无需预留很大的 OSS 容量，按量使用即可。一个合理的首年估算是：

| 数据 | 预计容量 |
|---|---:|
| 最近 30 天业务库每日备份 | 约 0.5 GB，压缩后更小 |
| 12 个月每周长期备份 | 约 0.8 GB，压缩后更小 |
| 10 个 wow-db Release | 约 1.4 GB |
| 清单、校验和和日志 | 小于 0.1 GB |
| 安全余量 | 2–5 GB |

因此初期按 5–10 GB 估算已经充足。OSS 是按实际用量计费，无需因为估算值提前创建固定大小的磁盘。

如果把全部 SimC HTML 也上传 OSS，增长会明显加快。建议默认只备份业务库和 wow-db 发布资产；SimC 原始产物按需归档，不作为永久备份。

### 5.3 生命周期策略

建议：

- 业务库每日备份：30 天后删除。
- 每周备份：保留 12 个月。
- 每月备份：长期保留或保留 24 个月。
- wow-db Release：保留当前版和若干历史版，不自动删除当前锁定版本。
- 非当前对象版本：30–90 天后清理。
- 未完成的分片上传：7 天后清理。

重要备份可在确认恢复流程后转为低频访问，但不要把频繁恢复所需的最近备份直接转为归档类型。

### 5.4 灾备副本与恢复目标

同地域 OSS 只解决 ECS/云盘故障，不提供地域级灾备。第一阶段上线前应至少配置独立第二地域 OSS Bucket 和独立 KMS key 的每周加密副本；若暂不采购，地域故障 RPO/RTO 必须明确标为无保证。

容量和运维预算按以下目标规划：ECS/云盘故障 RPO <= 26 小时、RTO <= 4 小时；可用区故障 RTO <= 8 小时；跨地域故障在启用副本后 RPO <= 7 天、RTO <= 24 小时。跨地域复制必须由源 KMS 解包后使用目标地域 KMS 重新加密、重包 data key、生成新 manifest 并重签名，不能直接复制源地域密文；KMS 不可用时本地备份不承诺 RTO。跨地域复制失败必须告警，且每季度做一次 KMS 解密、ECS 重建和 DNS 切换演练。

## 6. 网络、域名与安全

### 带宽

页面本身流量不大，3 Mbps 可以起步，5 Mbps 体验更稳。wow-db 应通过同地域 OSS 内网下载，不占用 ECS 公网带宽。图标和静态资源后续可以放 CDN，但当前不是必需。

### 地域

优先选择距离主要用户较近、且与 OSS/ACR 一致的大陆地域，例如上海、杭州或深圳。不要让 ECS 和 OSS 跨地域，否则会增加延迟和流量成本。

### 大陆部署前置条件

如果 ECS 位于中国大陆并通过自有域名向公网提供网页，需要考虑：

- 阿里云账号实名认证。
- 域名备案（ICP）。
- HTTPS 证书。
- 根据实际公开范围检查公安备案等要求。

如果暂时不准备备案，可以选择中国香港地域，但延迟、价格和跨境网络稳定性需要另行评估。

### 权限与密钥

- ECS 使用 RAM 角色访问 OSS，避免在磁盘保存长期 AccessKey。
- GitHub Actions 使用受限部署凭据；条件允许时采用 OIDC/RAM 联邦身份。
- 管理员密码只保存强哈希。
- 会话签名密钥和英雄榜会话不进入 Git、镜像或普通数据库备份。
- 安全组仅开放 80/443；SSH 限制来源 IP并使用密钥登录。
- 容器运行契约：Web 以非 root `UID:GID=10001:10001` 运行，root filesystem 只读；业务库数据盘可写挂载，wow-db 只读挂载，SimC/备份目录按 service 分权挂载。
- Node 容器监听 `0.0.0.0:3000`，主机仅映射到 `127.0.0.1:3100`；Nginx 负责 80/443 和 current/staged upstream 切换。当前代码监听 `127.0.0.1`，容器化前必须完成监听地址配置化。
- 主机权限按 `wowhelper-db` GID 10001、Web/job UID/GID 10001、`wowhelper-backup` UID 10002 和 POSIX ACL 配置；业务目录 `root:wowhelper-db`/`0770`，SQLite/WAL/SHM `0660`，备份目录 `wowhelper-backup:wowhelper-backup`/`0700`，备份文件 `0600`，禁止 `0777`。

## 7. 监控和告警

至少配置以下告警：

| 指标 | 建议阈值 |
|---|---|
| 数据盘使用率 | 70% 警告，85% 严重 |
| 内存使用率 | 连续 10 分钟超过 85% |
| CPU 使用率 | 连续 30 分钟超过 90% |
| 最近业务备份 | 超过 26 小时没有成功备份 |
| SQLite 完整性 | `quick_check` 非 `ok` 立即告警 |
| 服务健康检查 | 连续 3 次失败告警 |
| OSS 上传 | 每日备份任务失败立即告警 |

还应监控游客模拟队列长度、单次模拟耗时、英雄榜会话是否过期以及 wow-db Build 是否与锁定清单一致。

## 8. 推荐采购清单

当前阶段建议从以下配置开始：

```text
ECS：4 vCPU / 8 GiB，Ubuntu 24.04 x86_64
系统盘：40 GiB
独立数据盘：80 GiB ESSD Entry/PL0
公网：3–5 Mbps 或按流量付费
OSS：同地域私有标准存储 Bucket，预计首年 5–10 GB
云盘自动快照：每日一次，保留 7 天
域名和 HTTPS：大陆地域需先完成备案
ACR：第一阶段必需，使用与 ECS 同地域的镜像仓库保存不可变 digest
```

购买时无需一次性购买很高配置。数据盘和 OSS 可以扩容；ECS 也可以在观察一到两周的 SimC 峰值后升级。第一阶段最应避免的是选用 1 核 2 GB，以及让业务库在本地和云端同时可写。
